## Outcome

FillNest communicates the result, real scope, and available recovery path of a
user-initiated operation consistently. The Inline Picker has one field-scoped
Action Outcome Bar as its only Undo entry. Side Panel operations share the
same outcome vocabulary and invalidation model; Task 011 owns the final
navigation-adjacent Side Panel result-region layout.

## Confirmed Decisions

- The Picker Action Outcome Bar replaces the Picker header Undo control as the
  only Picker Undo entry.
- A Picker Undo belongs only to the same resolved `FieldProfile` that created
  it. It remains available after the Picker closes and reopens on that Field;
  no different Field may display or execute it.
- Every successful FillNest state mutation invalidates every previously
  available Undo. This includes Template, Binding, Site Data, Website Access,
  activation, Restore, Reset, and a successful Insert that updates usage.
  Opening or closing UI, navigation, Search, filtering, focus movement,
  cancelled actions, and failed actions are not mutations and do not invalidate
  Undo.
- Invalidation is silent: the stale Undo is removed with no explanatory
  notification or error.
- A successful new Template save shows that the Template was saved and bound
  to the current Field, but creates no Undo. The user can directly Delete that
  new Template through the established deletion flow.
- With no current outcome, the Picker shows ordinary Field context and no
  disabled Undo affordance. A successful Undo shows its restored/reverted
  outcome but creates no second Undo. A non-Undo outcome returns to ordinary
  context when the Picker closes, the user changes Field, or a later operation
  replaces it. A still-valid same-Field Undo outcome is the exception: it
  returns with its Action Outcome Bar when that Field's Picker reopens.
- Save everywhere, Save a copy for this field or Shared Template Set, Bind, Remove from this field,
  Delete template everywhere, and batch Delete retain Undo because their prior
  state cannot be recovered through an ordinary direct action.
- Side Panel has one current result. A new successful operation replaces the
  old result; results never queue or coexist. State controls (Global
  Activation, Origin Activation, and Page Status Control) communicate through
  their own Active/Pause state and do not produce a separate result message.
- A current-result action, including `Delete N newly Global Templates` after
  Clear site data, follows the same global invalidation rule as Undo and
  disappears silently after any successful FillNest mutation.
- Task 011 removes the current bottom-fixed Side Panel Undo bar and collapsed
  handle, removes the standalone Side Panel title, and delivers the permanent
  result region directly below the navigation. Task 010 must not make that
  header or layout change.

- Introduce a single, testable mutation boundary that invalidates pending Undo
  across Picker and Side Panel contexts. Existing record-revision checks stay
  as a fail-closed persistence safeguard; they no longer define the full
  user-visible invalidation policy.

- Preserve same-Field close/reopen Undo availability and prohibit cross-Field
  display or execution.
- Make Picker and current Side Panel Undo labels and completion messages use
  the shared vocabulary and the new invalidation policy.
- Preserve the existing Delete confirmation rules, typed `delete` boundary,
  repository atomicity, and plain-text-only insertion model.
- Add focused unit/component and headed extension evidence for outcome scope,
  undo invalidation, Field isolation, and accessible interaction.

## Boundaries And Stop Conditions

- Task 011 is the required consumer of the Task 010 Side Panel outcome model.
  Task 010 does not claim delivery of the final Side Panel result-region
  presentation before Task 011 is accepted and implemented.
- Stop for user direction if making all successful mutations observable to the
  Undo model requires persistent Undo history, relaxation of atomic Repository
  writes, a new permission, or a backend/network capability.
- Stop if a proposed message would expose a Template body, Field value, raw
  page data, or an unrelated later action beyond the established Preview and
  privacy rules.
- Stop if a compatibility change belongs to Task 012, 013, or 014 rather than
  this feedback contract.

## Acceptance Criteria

- No Picker header Undo control remains; the Action Outcome Bar is the sole
  Picker Undo entry.
- An undoable Picker result survives Picker close/reopen only for its original
  `FieldProfile`; it never leaks to another Field.
- Every successful FillNest mutation silently invalidates prior Undo, including
  successful Insert usage updates and permission/activation/Restore/Reset
  writes; no-op, failed, and cancelled actions do not.
- New Template creation is clearly reported but does not receive Undo.
- Every listed outcome accurately states its scope and never confuses removal
  from one Field with deletion from the Template Library.
- Side Panel uses the same semantic model and has at most one current result;
  final placement remains Task 011.
- Existing single-delete and whole-library-delete safeguards remain intact.

## Addendum — Task 020 Logical Page Matching (2026-09-01)

Bounded amendment raised by Task 020's implementation and accepted into this
contract rather than left as a silent carve-out. It narrows one rule and adds
two Outcome Vocabulary rows; nothing else in this contract changes.

### Mutation boundary applies to user-initiated mutations

The rule above reads "Every successful FillNest state mutation invalidates
every previously available Undo." Task 020 added an internal write the user
never asks for and never sees: recording an opaque Page Observation, which
the content script performs on its own whenever an eligible Field is focused
on a bound Page.

Treating that write as an invalidating mutation produced a real defect. The
content script re-records an Observation on every Business broadcast, so an
Observation write broadcast a further change, which erased the outcome
message of whatever the user had genuinely just done. A user who clicked
Bind could see their confirmation vanish for reasons no surface explained.

The boundary is therefore narrowed to **user-initiated** state mutations. An
Observation write is background bookkeeping: no surface displays one, no user
action creates one, and nothing observable depends on it, so it neither
invalidates Undo nor broadcasts. Every mutation the original rule enumerates
— Template, Binding, Site Data, Website Access, activation, Restore, Reset,
and usage-updating Insert — is user-initiated and continues to invalidate
exactly as before.

### Outcome Vocabulary additions

| Outcome | Message | Undo |
| --- | --- | --- |
| Logical Page confirmed | Reused your existing Templates for this page. | No |
| Logical Page Matching stopped | Stopped matching `<origin><route pattern>`. | No |

Both follow the established no-Undo pattern of a new Template save: the
result is reported plainly, prior transient Undo is invalidated, and no Undo
is offered. Task 014 requires this — confirmation "creates no Inline Picker
Undo", and separation "provides no separate Picker Undo".

The confirmed outcome carries one narrow exception to "a non-Undo outcome
returns to ordinary context when the user changes Field". Confirming
re-identifies the *same* focused Field as the canonical one, so the Field
Profile changes underneath a user who never moved. The message is carried
across that single transition, keyed to the Field it was produced for; a
genuine later Field change clears it as the rule requires.
